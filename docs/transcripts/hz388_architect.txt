**A. Python log buffering**
`docker compose logs -f train` collects the container’s stdout and stderr. The stage messages use `print()`, which writes to stdout. Since Compose does not allocate a TTY by default, Python normally block-buffers stdout; while the process is running, messages may not appear promptly and may only show after the buffer fills or the process exits.

Set `PYTHONUNBUFFERED=1` in the image or Compose environment, or run Python with `-u`. That makes the `print()` output available to `docker compose logs -f` as it is produced.

**B. Stopping workers**
The train and infer loops run indefinitely and have no shutdown handler. Compose sends `SIGTERM` when stopping a service, then sends `SIGKILL` if the process has not exited by the grace-period deadline. A container’s PID 1 has special signal behavior on Linux: signals with their default action may be ignored unless the process handles them. With a worker directly as PID 1 and no `SIGTERM` handler, it may therefore sit until Compose’s timeout and be killed. Even if the process does receive the default terminating signal, it can exit abruptly during a write.

A small shutdown handler should set a stop flag; the loop can finish its current operation and then exit. Use an interruptible wait such as `Event.wait(timeout)` instead of `time.sleep()` so it does not wait out the full poll interval after a stop request.

You can compare behavior by stopping the train service with a short timeout and inspecting its exit code:

```sh
docker compose stop --timeout 2 train
docker inspect "$(docker compose ps -aq train)" --format '{{.State.ExitCode}}'
```

Before adding a handler, a forced stop commonly produces exit code `137`; after, the worker should log that shutdown was requested and exit cleanly, typically with code `0`. The precise pre-fix result depends on how the container runtime and process handle the signal, so the log and elapsed stop time are useful evidence too.

`init: true` is helpful for signal forwarding and reaping child processes, but it is not a substitute for application shutdown handling. It can forward `SIGTERM` to the worker; without a handler, that still does not give the worker a chance to finish an in-progress operation or perform orderly cleanup.

**C. Named-volume ownership and dashboard health**
A new named volume is initialized from the image’s directory at the mount path when Docker performs volume copy-up. Its ownership comes from that directory’s ownership in the image, not from the container’s configured non-root `USER`. If the directory is root-owned, the non-root process may be unable to write to it. Create the mount directory in the image and assign it to the app’s UID/GID before first use; existing named volumes retain their existing ownership and may need separate handling.

The dashboard healthcheck can use Python’s standard library, already present in the slim image, to request Streamlit’s health endpoint at `http://127.0.0.1:8501/_stcore/health`. `urllib.request.urlopen()` can return a failing healthcheck status on connection or HTTP errors, without adding `curl`.
